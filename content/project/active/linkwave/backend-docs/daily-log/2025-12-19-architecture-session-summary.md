# 아키텍처 설계 세션 요약 (2025-12-19)

이 문서는 Linkwave 프로젝트의 백엔드 아키텍처를 개선하기 위해 논의했던 내용과 결정사항, 그리고 그 과정에서 얻은 기술적 인사이트를 정리한 문서입니다.

## 1. 초기 요구사항 및 목표

-   기존 코드베이스와 문서를 분석하여 프로젝트 파악
-   JPA와 MyBatis를 함께 사용하는 의미 있는 아키텍처 수립 (CQRS 패턴 도입)
-   단순 회원가입, 로그인, UMS 메시지 생성 기능에 대한 구현 가이드 업데이트
-   단순 구현을 넘어, 각 기술 결정의 배경(Why)과 인사이트 제공

## 2. 핵심 아키텍처 진화 과정

우리의 아키텍처는 논의를 거듭하며 다음과 같이 진화했습니다.

1.  **[v1] CQRS 패턴 도입:**
    -   **Command (데이터 변경):** JPA를 사용하여 객체 지향 설계와 트랜잭션 관리의 이점을 극대화.
    -   **Query (데이터 조회):** MyBatis를 사용하여 복잡하고 최적화된 SQL 성능을 보장.

2.  **[v2] UMS 기능의 문제점 발견:**
    -   단일 `ums_msg` 테이블을 웹 앱(Producer)과 외부 에이전트(Consumer)가 공유할 때 발생하는 동시성, 성능, 확장성 문제를 인식.

3.  **[v3] 내부 스케줄러를 이용한 '폴링' 모델:**
    -   외부 에이전트를 변경할 수 없다는 제약사항을 반영.
    -   **`ums_request` (요청 보관소)**와 **`ums_msg` (발송 준비실)** 테이블을 분리.
    -   Linkwave 내부에 `@Scheduled` 스케줄러를 두어, 주기적으로 `ums_request`를 읽어 `ums_msg`로 옮기는 '폴링' 방식 제안.

4.  **[v4] 'Push + Pull' 하이브리드 모델:**
    -   고정 시간 폴링의 비효율성(서버 부하, 지연)을 개선.
    -   **즉시 발송:** Spring의 `ApplicationEvent`를 이용한 **Push 방식**으로 실시간 처리.
    -   **예약 발송:** `@Scheduled` 스케줄러를 이용한 **Pull 방식**으로 효율적인 처리.

5.  **[v5] 'Closed-Loop' 아키텍처 완성:**
    -   `ums_log` 테이블의 존재와 통계 기능 요구사항을 반영.
    -   **`LogAggregator`** 라는 내부 스케줄러가 `ums_log`를 읽어 두 가지 작업을 수행:
        1.  `ums_request` 테이블에 최종 상태(`COMPLETED`/`FAILED`)를 피드백하여 데이터 흐름의 고리를 닫음(Close the loop).
        2.  `stats_*` 같은 통계용 요약 테이블을 생성하여 안전하고 빠른 조회를 지원.
    -   결과적으로 `ums_request`가 전체 라이프사이클을 관리하는 **'마스터 테이블'**이 되어, 별도의 `history` 테이블 없이 데이터 중복을 제거하고 구조를 단순화.

## 3. 주요 결정 및 기술적 인사이트

-   **CQRS:** 단순히 두 기술을 섞는 것이 아니라, '명령'과 '조회'라는 역할에 따라 명확히 분리함으로써 시스템의 유연성과 확장성을 확보했습니다.
-   **Polling vs. Event-Driven:** 상황의 긴급성(Urgency)에 따라 **Push와 Pull 방식을 조합**하는 하이브리드 설계가 반응성과 효율성을 모두 잡는 효과적인 방법임을 확인했습니다.
-   **DB Replication과 Self-Contained Events:** 분산 환경(DB 복제)에서는 **'이벤트 자체에 완전한 정보를 담아'** 전달함으로써, 복제 지연(Lag)으로 인한 데이터 불일치 문제를 원천적으로 방지할 수 있습니다.
-   **CQRS for Analytics:** 트랜잭션 처리(OLTP) 테이블(`ums_log`)을 분석/보고용(OLAP)으로 직접 사용하는 것의 위험성을 인지하고, **'통계용 조회 모델'(`stats_*` 테이블)을 별도 구축**하여 시스템의 성능과 보안을 모두 확보했습니다.
-   **Closed-Loop Architecture:** 데이터의 흐름이 시작점(`ums_request`)에서 출발하여, 외부 시스템을 거친 후 다시 시작점으로 돌아와 상태를 완결시키는 '닫힌 고리' 구조가 데이터의 정합성과 추적 용이성을 크게 향상시킴을 확인했습니다.

## 4. 논의된 기술 스택 및 개념

-   **Spring Framework:**
    -   `@Scheduled`: 주기적인 작업을 위한 스케줄러.
    -   `ApplicationEventPublisher`: Spring 내장 이벤트 발행 기능.
    -   `@EventListener`: 이벤트 구독 및 처리.
    -   `@Async` & `@EnableAsync`: 간단하게 비동기 백그라운드 스레드를 활성화하는 방법.
    -   `@TransactionalEventListener`: DB 트랜잭션의 생명주기에 맞춰 이벤트를 처리하여 데이터 정합성을 높이는 고급 기법.
-   **Message Broker (개념 학습):**
    -   **RabbitMQ:** 유연한 라우팅과 예약 발송 등 풍부한 기능이 장점인 '스마트 브로커'. MSA 간의 작업 처리(Task-queuing)에 적합.
    -   **Kafka:** 압도적인 처리량과 데이터 보관/재처리가 장점인 '분산 로그 스트리밍 플랫폼'. 대규모 이벤트 수집 및 분석에 적합.
-   **Database:**
    -   **Replication Lag:** DB 복제 환경에서 항상 고려해야 할 지연 문제.
    -   **Pessimistic Lock:** `SELECT ... FOR UPDATE SKIP LOCKED` 등, 동시성 제어를 위한 데이터베이스 잠금 전략.

이번 아키텍처 설계 세션은 프로토타입을 넘어, 실제 운영 환경의 안정성과 확장성까지 고려한 견고한 시스템의 청사진을 그리는 매우 의미 있는 과정이었습니다.
