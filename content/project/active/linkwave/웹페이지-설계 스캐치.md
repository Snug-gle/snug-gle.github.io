# 문자 발송 웹페이지 설계

## 1. 개요

### 1.1 목적
사용자가 문자 메시지(SMS, LMS, MMS, 카카오톡, RCS)를 입력하고 발송 요청할 수 있는 웹 인터페이스 제공

### 1.2 기술 스택
- **프론트엔드**: React, JavaScript
- **백엔드**: Spring Boot 4.0
- **데이터베이스**: MySQL (향후 Oracle, PostgreSQL 확장)

### 1.3 역할 범위
웹페이지는 **발송 요청 접수 및 DB 저장**만 담당합니다. 실제 발송은 별도의 발송 에이전트가 처리합니다.

### 2.2 데이터베이스 분리 전략

**웹 서비스용 DB (Web DB)**
- 목적: 사용자 인터페이스 및 부가 기능 지원
- 특징: 빈번한 읽기/쓰기, 사용자 경험 최적화
- 테이블:
  - 주소록 관리
  - 발신번호 리스트
  - 문자 보관함
  - 공유 주소록
  - 사용자측 고객 리스트

**발송용 DB (Message DB)**
- 목적: 메시지 발송 처리 및 이력 관리
- 특징: 대용량 처리, 발송 성능 최적화
- 테이블:
  - `ums_msg`: 발송 요청 및 상태 관리
  - `ums_log_{YYYYMM}`: 월별 파티셔닝된 발송 이력

**데이터 동기화 모듈**
- 역할: Web DB → Message DB 데이터 전송
- 구현 방식:
  - 실시간성 물량: 즉시 동기화 (TRAFFIC_TYPE: real)
  - 배치성 물량: 배치 처리 (TRAFFIC_TYPE: batch)
  - 일반 물량: 준실시간 동기화 (TRAFFIC_TYPE: normal)

### 2.3 중복 발송 방지

**중복 조건**: `전화번호 + 메시지 내용`
- 동일한 번호에 동일한 내용의 메시지가 일정 시간 내 재발송되는 것을 방지
- 구현:
  - `ums_msg` 테이블에 `(PHONE + MSG)` 해시값 저장
  - 일정 시간(예: 10분) 내 중복 요청 검증
  - 중복 발송 옵션 제공 (사용자 선택)

## 3. 프론트엔드 설계 (React)

### 3.1 주요 화면

#### 3.1.1 메인 네비게이션
```
┌─────────────────────────────────────────────┐
│ 로고  [SMS] [LMS] [MMS] [카카오톡] [RCS]    │
└─────────────────────────────────────────────┘
```

각 메시지 타입별로 탭 또는 메뉴가 분리되어 있으며, 선택한 타입에 따라 발송 화면이 전환됩니다.

#### 3.1.2 메시지 작성 화면 (공통)
각 메시지 타입(SMS/LMS/MMS/카카오톡/RCS)마다 개별 화면이 있으며, 공통 구성 요소는 다음과 같습니다:

1. **수신자 입력**
   - 직접 입력 (단일: 01012345678, 다중: 콤마 구분)
   - 엑셀 업로드 (대량 발송)
   - 주소록에서 선택
   - 그룹 선택

2. **발신번호 선택**
   - 드롭다운 리스트로 등록된 발신번호 선택

3. **메시지 내용 입력**
   - 텍스트 에디터
   - 바이트 수 실시간 표시 (SMS: 90byte, LMS: 2000byte)
   - 치환 변수 지원 (#{이름}, #{회사명} 등)

4. **타입별 추가 기능**
   - **MMS**: 이미지 첨부 (최대 300KB, JPG/PNG)
   - **카카오톡**: 템플릿 선택, 버튼 설정, 이미지 첨부
   - **RCS**: 미디어 첨부, 버튼/액션 설정, 카드형 메시지 구성

5. **발송 옵션**
   - 즉시 발송 / 예약 발송 (날짜/시간 선택)
   - 중복 제거 옵션

6. **발송 버튼**
   - "발송하기" / "예약하기"
   - 예상 비용 표시

#### 3.1.3 발송 이력 화면
```
┌──────────────────────────────────────────────────────────┐
│ [조회] 기간: [2025-12-01] ~ [2025-12-02]  [검색]         │
│ 상태: [전체▾] [PENDING] [SENT] [FAILED]                  │
├──────────────────────────────────────────────────────────┤
│ 메시지ID  │ 타입 │ 수신자수 │ 상태   │ 요청시간         │

│ MSG_002   │ LMS  │ 50      │ PENDING│ 2025-12-02 15:00│
```

#### 4.3.1 관리자(본사) 테이블

##### 4.3.1.1 companies (회사 리스트)
```sql
CREATE TABLE companies (
    company_id VARCHAR(50) PRIMARY KEY,
    company_name VARCHAR(100) NOT NULL,
    business_number VARCHAR(20) UNIQUE,
    contact_email VARCHAR(100),
    contact_phone VARCHAR(20),
    status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE', -- ACTIVE, INACTIVE, SUSPENDED
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_status (status)
);
```

##### 4.3.1.2 users (사용자 리스트)
```sql
CREATE TABLE users (
    user_id VARCHAR(50) PRIMARY KEY,
    company_id VARCHAR(50) NOT NULL,
    username VARCHAR(50) NOT NULL UNIQUE,
    password VARCHAR(255) NOT NULL,
    email VARCHAR(100),
    phone VARCHAR(20),
    role VARCHAR(20) NOT NULL, -- ADMIN, USER, MANAGER
    status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (company_id) REFERENCES companies(company_id),
    INDEX idx_company_id (company_id),
    INDEX idx_username (username),
    INDEX idx_status (status)
);
```

##### 4.3.1.3 admin_sender_numbers (관리자 발신번호)
```sql
CREATE TABLE admin_sender_numbers (
    sender_number_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    company_id VARCHAR(50) NOT NULL,
    sender_number VARCHAR(16) NOT NULL,
    is_verified BOOLEAN DEFAULT FALSE,
    verification_date DATETIME NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (company_id) REFERENCES companies(company_id),
    UNIQUE KEY uk_company_sender (company_id, sender_number),
    INDEX idx_company_id (company_id)
);
```

#### 4.3.2 사용자(고객사) Web DB 테이블

##### 4.3.2.1 sender_numbers (발신번호 리스트)
```sql
CREATE TABLE sender_numbers (
    sender_number_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id VARCHAR(50) NOT NULL,
    sender_number VARCHAR(16) NOT NULL,
    is_verified BOOLEAN DEFAULT FALSE,
    is_default BOOLEAN DEFAULT FALSE,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(user_id),
    UNIQUE KEY uk_user_sender (user_id, sender_number),
    INDEX idx_user_id (user_id)
```

### 4.4 메시지 발송 흐름

```
1. 사용자가 웹페이지에서 메시지 작성 및 발송 요청
   ↓
2. Controller에서 요청 수신 및 검증
   - 필수 필드 검증 (messageType, senderNumber, recipients, content)
   - 바이트 수 검증 (SMS: 90byte, LMS: 2000byte)
   - 파일 크기 검증 (MMS: 300KB)
   - 중복 발송 체크 (옵션 설정 시)
   ↓
3. MessageService에서 비즈니스 로직 처리
   - Web DB에 주소록/보관함 관련 데이터 저장 (필요 시)
   - TRAFFIC_TYPE 결정 (real/normal/batch)
   - CLIENT_KEY 생성 (datetime + business name + random string)
   - DEDUP_HASH 생성 (MD5(PHONE + MSG))
   ↓
4. 데이터 동기화 모듈 호출
   - Web DB → Message DB (ums_msg) 데이터 전송

   [실시간 물량 (TRAFFIC_TYPE: real)]
   - 즉시 동기화
   - MSG_STATUS: 'ready'

   [일반 물량 (TRAFFIC_TYPE: normal)]
   - 준실시간 동기화 (수초 내)
   - MSG_STATUS: 'ready'

   [배치 물량 (TRAFFIC_TYPE: batch)]
   - 배치 처리 (스케줄링)
   - MSG_STATUS: 'ready'

   [예약 발송]
   - REQ_DATE에 미래 시간 설정
   - MSG_STATUS: 'ready'
   ↓
5. 사용자에게 Response 반환
   {
     "clientKey": "20251202143000_CompanyA_A3F8D2",
     "status": "ACCEPTED",
     "trafficType": "normal",
     "requestedAt": "2025-12-02T14:30:00",
     "recipientCount": 2
   }
   ↓
6. 발송 에이전트가 Message DB 폴링
   - TRAFFIC_TYPE 우선순위: real > normal > batch
   - MSG_STATUS = 'ready' AND REQ_DATE <= NOW()
   - 조회 후 MSG_STATUS → 'pre-send'
   ↓
7. 발송 에이전트 처리
   - RabbitMQ로 발행
   - 중계 서버 발송
   - 발송 결과 업데이트
     - ums_msg: MSG_STATUS → 'complete'
     - ums_log_{YYYYMM}: 발송 이력 기록
```

### 4.5 데이터 동기화 모듈 설계

```java
@Service
@RequiredArgsConstructor
public class MessageSyncService {

    private final WebDbRepository webDbRepository;
    private final MessageDbRepository messageDbRepository;
    private final DedupService dedupService;

    /**
     * Web DB → Message DB 동기화
     */
    @Transactional
    public SyncResult syncToMessageDb(MessageRequest request) {
        // 1. 중복 체크
        String dedupHash = dedupService.generateHash(request.getPhone(), request.getContent());
        if (dedupService.isDuplicate(dedupHash, request.getDedupWindowMinutes())) {
            throw new DuplicateMessageException("중복 발송 요청");
        }

        // 2. CLIENT_KEY 생성
        String clientKey = generateClientKey(request);

        // 3. ums_msg 엔티티 생성
        UmsMsg umsMsg = UmsMsg.builder()
            .clientKey(clientKey)
            .reqCh(request.getMessageType())
            .trafficType(determineTrafficType(request))
            .msgStatus("ready")
            .reqDate(request.getScheduledAt() != null ?
                     request.getScheduledAt() : LocalDateTime.now())
            .callbackNumber(request.getSenderNumber())
            .phone(request.getPhone())
            .msg(request.getContent())
            .title(request.getTitle())
            .dedupHash(dedupHash)
            // ... 기타 필드 매핑
            .build();

        // 4. Message DB 저장
        messageDbRepository.save(umsMsg);

        return SyncResult.success(clientKey);
    }

    /**
     * TRAFFIC_TYPE 결정 로직
     */
    private String determineTrafficType(MessageRequest request) {
        // 사용자 지정 우선
        if (request.getTrafficType() != null) {
            return request.getTrafficType();
        }

        // 예약 발송은 batch
        if (request.getScheduledAt() != null &&
            request.getScheduledAt().isAfter(LocalDateTime.now().plusMinutes(10))) {
            return "batch";
        }

        // 대량 발송은 batch
        if (request.getRecipientCount() > 100) {
            return "batch";
        }

        // 기본은 normal
        return "normal";
    }

    /**
     * CLIENT_KEY 생성
     * 형식: {datetime}{business_name}{random_string}
     */
    private String generateClientKey(MessageRequest request) {
        String datetime = LocalDateTime.now().format(
            DateTimeFormatter.ofPattern("yyyyMMddHHmmss"));
        String businessName = request.getCompanyId().replaceAll("[^a-zA-Z0-9]", "");
        String randomString = RandomStringUtils.randomAlphanumeric(8).toUpperCase();

        return String.format("%s_%s_%s", datetime, businessName, randomString);
    }
}
```

### 4.6 중복 발송 방지 구현

```java
@Service
@RequiredArgsConstructor
public class DedupService {

    private final UmsMsgRepository umsMsgRepository;

    /**
     * 중복 해시 생성
     */
    public String generateHash(String phone, String content) {
        String combined = phone + "|" + content;
        return DigestUtils.md5Hex(combined);
    }

    /**
     * 중복 체크
     * @param dedupHash 중복 체크용 해시
     * @param windowMinutes 중복 체크 시간 윈도우 (분)
     * @return true: 중복, false: 중복 아님
     */
    public boolean isDuplicate(String dedupHash, int windowMinutes) {
        LocalDateTime threshold = LocalDateTime.now().minusMinutes(windowMinutes);

        return umsMsgRepository.existsByDedupHashAndReqDateAfter(
            dedupHash, threshold);
    }
}
```

### 4.7 통계 정보 제공 (ETC 컬럼 활용)

**ETC 컬럼 활용 예시:**

- **ETC3 (COST)**: 발송 비용

## 부록: 기술 의사결정 기록

### A.1 왜 DB를 Web DB와 Message DB로 분리하는가?
- **성능 최적화**: 웹 서비스 DB와 발송 처리 DB를 분리하여 각각 최적화
- **부하 분산**: 사용자 트래픽과 발송 처리 부하를 독립적으로 관리
- **확장성**: 각 DB를 독립적으로 스케일 업/아웃 가능
- **장애 격리**: Web DB 장애 시에도 발송 에이전트는 정상 동작
- **관심사 분리**: 사용자 관련 데이터와 발송 데이터의 명확한 분리

### A.2 왜 웹페이지에서 RabbitMQ를 사용하지 않는가?
- **관심사의 분리**: 웹페이지는 사용자 요청 접수만 담당, 발송은 에이전트가 담당
- **단순성**: 웹 API는 DB 저장만 하므로 구조가 단순하고 빠름
- **독립성**: RabbitMQ 장애 시에도 웹페이지는 정상 작동 (요청 접수 가능)
- **확장성**: 발송 에이전트를 독립적으로 Scale-Out 가능

### A.3 TRAFFIC_TYPE을 통한 우선순위 관리
- **real (실시간/중요)**: 인증번호, 알림 등 즉시 발송 필요
- **normal (일반)**: 일반적인 메시지 발송
- **batch (마케팅/광고)**: 대량 발송, 시간 여유 있음
- **장점**:
  - 중요 메시지 우선 처리
  - 발송 에이전트의 효율적인 리소스 분배
  - 대량 발송으로 인한 중요 메시지 지연 방지

### A.4 중복 발송 방지 전략
- **중복 조건**: 전화번호 + 메시지 내용
- **해시 기반**: MD5(PHONE + MSG)로 빠른 조회
- **시간 윈도우**: 설정 가능한 시간 내(기본 10분) 중복 체크
- **사용자 선택권**: 중복 발송 허용/차단 옵션 제공

### A.5 ums_log 월별 파티셔닝
- **대용량 데이터 처리**: 발송 이력은 빠르게 증가하는 특성
- **조회 성능**: 특정 월 데이터만 조회하여 성능 향상
- **데이터 관리**: 오래된 데이터 아카이빙 및 삭제 용이
- **백업/복구**: 월별 테이블로 백업 및 복구 전략 수립 용이

### A.6 ETC 컬럼 활용 전략
- **유연성**: 고객사별 다양한 요구사항 수용
- **통계 정보**: ETC1-3을 표준 통계 필드로 활용
  - ETC1: 성공 여부 (Y/N)
  - ETC2: 실패 사유
  - ETC3: 발송 비용
- **확장성**: 나머지 ETC4-6은 향후 확장 예비

### A.7 왜 JPA/Hibernate인가?
- 다중 데이터베이스 지원 용이 (MySQL, Oracle, PostgreSQL)
- 객체 지향적 개발
- Spring Boot와의 강력한 통합

### A.8 메시지 타입별 화면 분리 이유
- **사용자 경험**: 각 타입마다 입력 필드와 옵션이 다름 (SMS는 단순, RCS는 복잡)
- **명확성**: 사용자가 현재 어떤 타입을 발송하는지 명확히 인지
- **유지보수**: 타입별 로직이 분리되어 수정 용이

### A.9 관리자(본사) vs 사용자(고객사) 구조
- **멀티 테넌시**: 하나의 시스템에서 여러 회사(고객사) 관리
- **회사별 격리**: 각 회사의 데이터와 사용자를 명확히 분리
- **중앙 관리**: 본사에서 회사 및 사용자 관리, 발신번호 승인
- **확장성**: 새로운 고객사 추가가 용이

#### 11.1.1 분산 트랜잭션 처리
**문제**: Web DB → Message DB 동기화 실패 시 데이터 불일치

**해결 방안**:
```java
@Service
@RequiredArgsConstructor
public class MessageSyncService {

    /**
     * Saga 패턴 기반 동기화
     */
    @Transactional
    public SyncResult syncWithSaga(MessageRequest request) {
        String clientKey = null;
        try {
            // 1. Web DB 저장
            saveToWebDb(request);

            // 2. Message DB 동기화
            clientKey = syncToMessageDb(request);

            return SyncResult.success(clientKey);

        } catch (Exception e) {
            // 3. 보상 트랜잭션 또는 sync_queue 등록
            if (clientKey != null) {
                rollbackMessageDb(clientKey);
            }
            registerToSyncQueue(request, e.getMessage());

            throw new SyncFailedException("동기화 실패", e);
        }
    }

    /**
     * 동기화 실패 시 재처리 큐 등록
     */
    private void registerToSyncQueue(MessageRequest request, String errorMsg) {
        SyncQueue queue = SyncQueue.builder()
            .clientKey(request.getClientKey())
            .syncStatus("FAILED")
            .syncType("MESSAGE_SYNC")
            .payload(toJson(request))
            .errorMessage(errorMsg)
            .retryCount(0)
            .nextRetryAt(LocalDateTime.now().plusMinutes(5))
            .build();

        syncQueueRepository.save(queue);
    }
}
```

#### 11.1.2 동기화 재처리 스케줄러

```java
@Component
@RequiredArgsConstructor
public class SyncRetryScheduler {

    private final SyncQueueRepository syncQueueRepository;
    private final MessageSyncService messageSyncService;

    @Scheduled(fixedDelay = 60000) // 1분마다
    public void retryFailedSync() {
        LocalDateTime now = LocalDateTime.now();

        List<SyncQueue> failedQueues = syncQueueRepository
            .findBySyncStatusAndNextRetryAtBefore("FAILED", now);

        for (SyncQueue queue : failedQueues) {
            try {
                // 재시도
                messageSyncService.retrySync(queue);

                queue.setSyncStatus("SUCCESS");
                queue.setSyncedAt(now);

            } catch (Exception e) {
                queue.setRetryCount(queue.getRetryCount() + 1);

                if (queue.getRetryCount() >= queue.getMaxRetry()) {
                    queue.setSyncStatus("DEAD_LETTER");
                    // 알림 발송
                    notifyAdminAboutFailure(queue);
                } else {
                    queue.setNextRetryAt(calculateNextRetry(queue.getRetryCount()));
                }
            }
            syncQueueRepository.save(queue);
        }
    }
}
```

```java
        // 예약 발송 상태 확인
        if (!"ready".equals(message.getMsgStatus())) {
            throw new InvalidOperationException("이미 발송되었거나 처리 중입니다");
        }

        if (message.getReqDate().isBefore(LocalDateTime.now())) {
            throw new InvalidOperationException("발송 시간이 경과되었습니다");
        }

        // 상태 변경
        message.setMsgStatus("CANCELLED");
        umsMsgRepository.save(message);

        return ResponseEntity.noContent().build();
    }
}
```

```java
@Configuration
public class DataSourceConfig {

    @Bean
    @Primary
    public DataSource dataSource() {
        Map<Object, Object> dataSources = new HashMap<>();
        dataSources.put("master", masterDataSource());
        dataSources.put("slave", slaveDataSource());

        RoutingDataSource routingDataSource = new RoutingDataSource();
        routingDataSource.setTargetDataSources(dataSources);
        routingDataSource.setDefaultTargetDataSource(masterDataSource());

        return routingDataSource;
    }
}
```
