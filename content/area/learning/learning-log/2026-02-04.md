### 1. 역할 기반 분리 (Role-Based CQRS)

**핵심 개념**: 쿼리의 목적에 따라 기술 스택 분리

| 쿼리 목적 | 기술 스택 | 예시 |
|----------|----------|------|
| 상태 변경을 위한 조회 | JPA | findById (update용), existsBy (validation용) |
| 사용자에게 보여주기 위한 조회 | MyBatis | 목록 조회, 검색, 상세 보기 |

**핵심 질문**: "이 조회 결과로 무엇을 하는가?"

**네이밍 규칙**:
- Command: `{Entity}Repository` (JPA)
- Query: `{Entity}QueryMapper` (MyBatis)

**적용 결과**:
- `ContactRepository` → Command만 유지 (JPA)
- `ContactQueryMapper` → Query 전담 (MyBatis)
- QueryDSL 코드 제거

### 2. Mockito 테스트 어노테이션

#### @Mock vs @MockitoBean

| 어노테이션 | 환경 | 용도 |
|-----------|------|------|
| `@Mock` | 순수 Mockito | 단위 테스트 |
| `@MockitoBean` | Spring Boot | 슬라이스/통합 테스트 |

#### @InjectMocks

테스트 대상 객체를 생성하고 `@Mock` 객체들을 자동 주입

```java
@ExtendWith(MockitoExtension.class)
class ContactServiceTest {
    @Mock
    private ContactRepository contactRepository;
    
    @InjectMocks
    private ContactService contactService;  // Mock들이 자동 주입됨
}
```

#### ArgumentCaptor

Mock 메서드에 전달된 인자를 캡처하여 검증

```java
@Captor
ArgumentCaptor<Contact> contactCaptor;

verify(repository).save(contactCaptor.capture());
assertThat(contactCaptor.getValue().getName()).isEqualTo("홍길동");
```

## 주요 인사이트

> [!tip] 기술 선택의 기준
> 기술 스택 선택은 "무엇을 사용할까?"보다 "왜 사용하는가?"가 더 중요하다.
> JPA vs MyBatis 선택도 쿼리의 **목적**에 따라 결정해야 한다.

> [!note] 테스트 전략
> - 서비스 단위 테스트: `@Mock` + `@InjectMocks` (빠름)
> - 컨트롤러 슬라이스 테스트: `@WebMvcTest` + `@MockitoBean`
> - 통합 테스트: `@SpringBootTest` + 실제 DB
