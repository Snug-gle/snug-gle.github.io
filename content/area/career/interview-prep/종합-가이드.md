## 1. 나의 개발자 여정과 동기

### 왜 개발자가 되려고 하는가?

**핵심 동기:**
- **일을 통한 행복과 만족감**: 단순히 생계가 아닌, 가치 있는 일을 하고 싶음
- **더 나은 서비스 만들기**: 사용자에게 실질적인 도움을 주는 서비스 개발
- **경계를 넘는 웹 세계**: 지역과 국가를 넘어 전 세계 사람들에게 영향을 줄 수 있는 기술

### 커리어 방향성

**현대 기업들의 트렌드를 따르는 이유:**
- AI와 다양한 기술의 범람 속에서 혼자 방향을 정하기 어려움
- **이윤을 추구하는 기업들의 기술 스택을 지표로 삼기로 결정**
- 현재 주목하는 개발 방법론:
  - [[Upstream Development]] - 오픈소스 기여와 협업
  - [[TDD]] - 테스트 주도 개발
  - [[DDD]] - 도메인 주도 설계

### 성장 마인드셋

- **지속적인 학습**: PARA 방법론으로 체계적인 지식 관리
- **문서화 습관**: Obsidian vault를 통해 학습 내용, 프로젝트 경험, 일일 로그 기록
- **실천적 학습**: 이론 학습 후 반드시 프로젝트에 적용

## 3. 프로젝트 경험

### 3.1 Performance Tester (Frontend 전담, 5주)

> **기간**: 2025년 10월 ~ 11월 (약 5주)
> **역할**: Frontend Developer (프론트엔드 전체 담당)
> **기술 스택**: React 19, TypeScript, Vite, TanStack (Query/Table/Virtual), Tailwind CSS
> **팀**: 백엔드 개발자 2명과 협업

#### 프로젝트 개요
웹 애플리케이션의 성능 테스트 결과를 분석하고, 동적 값들 간의 상관관계를 자동으로 추출하여 JMeter 테스트 스크립트를 최적화하는 도구

#### 나의 기여
- **커밋 기여도**: 총 50개 커밋 중 30개 (60%)
- **대규모 코드 변경**: 606 insertions, 384 deletions (UI 개편)
- **전체 프론트엔드 설계 및 구현**: UI/UX 설계부터 성능 최적화까지

#### 주요 기술적 도전과 해결

**1. 대용량 데이터 테이블 렌더링 (가장 중요)**

**문제:**
- 10,000개 이상의 HTTP 요청 데이터를 테이블로 표시
- 초기 구현: 모든 행을 DOM에 렌더링 → 브라우저 멈춤

**해결 과정:**
1. **페이징 도입**: 100 → 500 → 1000개로 점진적 증가
2. **클라이언트 가상화**: TanStack Virtual 사용
3. **React Query 캐싱**: 5분 staleTime, 10분 gcTime

```typescript
// 최종 솔루션
const rowVirtualizer = useVirtualizer({
  count: data.length,
  getScrollElement: () => parentRef.current,
  estimateSize: () => 35,
  overscan: 10, // 버퍼로 10개 행 미리 렌더링
});
```

**결과:**
- 초기 렌더링: 5초 → 0.5초 (90% 감소)
- 메모리 사용량: 70% 감소
- 부드러운 스크롤 경험 제공

**2. 불필요한 API 요청 제거**

**발견한 문제들:**
- 중복 요청: 여러 컴포넌트에서 동일 데이터 요청
- 조건 없는 요청: perfTestId 없이도 요청 시도
- 무한 루프: 상태 변경이 useEffect 재트리거

**해결:**
```typescript
const { data } = useQuery({
  queryKey: ['data', perfTestId],
  queryFn: () => fetchData(perfTestId),
  enabled: !!perfTestId, // 조건부 실행
  staleTime: 1000 * 60 * 5, // 5분간 캐시 사용
});
```

**결과:**
- 네트워크 요청 80% 감소
- 불필요한 로딩 스피너 제거

**3. 상태 관리 전략**

- **전역 상태**: Context API (인증, 테마)
- **서버 상태**: React Query
- **로컬 상태**: useState
- **폼 상태**: React Hook Form

**4. 사용자 경험 개선**
- 검색 중 성능 테스트 변경 방지 (버튼 disable)
- 로딩 상태 시각화 (Spinner + Progress bar)
- 특수문자 유효성 검사
- 툴팁으로 긴 텍스트 미리보기
- 반응형 패널 레이아웃 (ResizablePanel)

#### 학습한 것

**React 19와 TanStack 생태계:**
- React Compiler의 자동 메모이제이션
- TanStack Query의 캐싱 전략
- TanStack Virtual의 가상화 렌더링
- TanStack Table의 고급 기능

**TypeScript 고급 활용:**
- 제네릭 활용한 재사용 가능한 Hook
- 타입 가드로 런타임 안정성
- Utility Types (Partial, Required, Pick)

**성능 최적화 기법:**
- 측정 기반 최적화 (React DevTools Profiler)
- Lazy Loading과 Code Splitting
- Debouncing과 Memoization

#### 면접에서 강조할 점

1. **점진적 개선**: 100 → 500 → 1000 페이징으로 최적점 발견
2. **측정과 검증**: React DevTools, Chrome DevTools로 병목 지점 파악
3. **사용자 중심**: UX 개선을 위한 로딩 상태, 에러 처리
4. **협업**: 백엔드와 API 스펙 논의, Git 협업

### 3.2 Rally-Point (개인 프로젝트, 진행 중)

> **기간**: 2025년 6월 ~ 진행 중
> **역할**: Full-stack Developer (개인 프로젝트)
> **기술 스택**: Spring Boot, Java 21, Kotlin, Kafka, Redis, Elasticsearch, Spring Batch
> **아키텍처**: MSA (Microservices Architecture)

#### 프로젝트 개요
테니스 코트 예약, 사용자 매칭, 중고 거래, 공지, 회원 관리 등을 제공하는 통합 플랫폼

#### 아키텍처 설계

**MSA 도메인 분리:**
- `user-service` (Java): 회원가입, 로그인, 권한
- `court-service` (Kotlin): 테니스장, 예약, 취소 (분산락, Redis)
- `match-service` (Kotlin): 매칭 신청, 결과 저장
- `market-service` (Java): 중고거래, 경매 기능
- `bid-service` (Java): 입찰 처리, 낙찰 스케줄링 (Kafka, WebSocket)
- `notification-service` (Java): 알림 전송 (Kafka Consumer)
- `search-service` (Kotlin): Elasticsearch 기반 검색
- `batch-service` (Kotlin): Spring Batch 작업 전용
- `gateway-service` (Java): API Gateway
- `notice-service` (Kotlin): 공지사항

#### 기술적 도전

**1. Redis 활용 전략**
- **캐싱**: 예약 현황 빠른 조회
- **세션 관리**: JWT 토큰 관리
- **분산 락**: 동시 예약 방지 (Redisson)
- **대기열 관리**: 예약 실패 사용자 대기 리스트

**2. Kafka 이벤트 기반 아키텍처**
- 예약 생성/취소 이벤트 발행
- 도메인 간 이벤트 전파
- 알림 시스템 연동
- 실패 처리와 재시도 전략 (DLQ)

**3. Spring Batch**
- 만료 예약 정리
- 보고서 생성 (일/주/월)
- 대기열 일괄 처리
- 데이터 아카이빙

**4. 개발 원칙 수립**

**레이어드 아키텍처:**
```
domain/     # 도메인 계층 (VO, Entity, DomainService)
application/ # 애플리케이션 계층 (DTO, UseCase, Controller)
infra/      # 인프라 계층 (Repository)
common/     # 공통 계층 (Config, Security, Exception)
```

**DDD 적용:**
- Value Object vs Entity 명확한 분리
- MapStruct로 명시적 변환
- 비즈니스 로직은 도메인 레이어에 집중

**보안 원칙:**
- JWT + Refresh Token 전략
- BCrypt (strength 12) 비밀번호 암호화
- Method Security (`@PreAuthorize`)
- 입력 검증 (Bean Validation)

**테스트 전략:**
- 단위 테스트: 80% 이상 목표
- 통합 테스트: 주요 API 100%
- Test Fixture 클래스 활용

#### 학습한 것

**MSA 설계:**
- Bounded Context 정의
- 도메인 간 통신 (Kafka, REST)
- API Gateway 패턴

**이벤트 기반 아키텍처:**
- Event Sourcing 개념
- Saga Pattern
- CQRS 이해

**운영 고려사항:**
- 모니터링 (Redis Insight, Kafka UI)
- 메시지 보장 (at-least-once)
- 문서화 (Spring REST Docs, Swagger)

#### 면접에서 강조할 점

1. **아키텍처 설계 능력**: MSA 도메인 분리, 이벤트 기반 설계
2. **실전 기술 적용**: Redis, Kafka, Elasticsearch 통합
3. **코드 품질**: 레이어드 아키텍처, DDD, 테스트 전략
4. **운영 고민**: 모니터링, 장애 대응, 문서화

### 7.2 기술 질문

#### Q1: 대용량 데이터를 어떻게 처리했나요?

"Performance Tester 프로젝트에서 10,000개 이상의 HTTP 요청 데이터를 테이블로 표시해야 했습니다.

초기에는 모든 데이터를 DOM에 렌더링했더니 브라우저가 멈추는 문제가 발생했습니다. 이를 해결하기 위해 세 가지 접근을 시도했습니다.

**첫째, 서버 사이드 페이징**을 도입했습니다. 처음에는 100개씩 데이터를 나눠 불러왔지만, 사용자가 계속 페이지를 넘겨야 하는 UX 문제가 있었습니다. 그래서 점진적으로 500개, 1000개로 늘렸고, 1000개가 적절한 균형점임을 발견했습니다.

**둘째, 클라이언트 가상화**를 적용했습니다. TanStack Virtual을 사용하여 화면에 보이는 행만 실제로 DOM에 렌더링하고, 나머지는 높이만 계산하여 스크롤 영역을 확보했습니다.

**셋째, React Query의 캐싱 전략**을 활용했습니다. `staleTime`을 5분, `gcTime`을 10분으로 설정하여 불필요한 재요청을 방지했습니다.

최종적으로 초기 렌더링 시간을 5초에서 0.5초로 90% 단축했고, 메모리 사용량도 70% 감소시켰습니다. 이 과정에서 성능 최적화는 측정과 점진적 개선이 중요하다는 것을 배웠습니다."

#### Q2: JPA N+1 문제를 어떻게 해결하나요?

"JPA N+1 문제는 연관 관계가 있는 엔티티를 조회할 때 발생하는 성능 문제입니다. Rally-Point 프로젝트에서 이 문제를 경험하고 여러 해결 방법을 학습했습니다.

**첫 번째 방법은 Fetch Join**입니다.
```java
@Query("SELECT u FROM UserJpaEntity u JOIN FETCH u.profile")
List<UserJpaEntity> findAllWithProfile();
```
이렇게 하면 한 번의 쿼리로 User와 Profile을 함께 가져올 수 있습니다.

**두 번째 방법은 EntityGraph**입니다.
```java
@EntityGraph(attributePaths = {"profile", "credential"})
List<UserJpaEntity> findAll();
```
EntityGraph는 동적으로 Fetch 전략을 변경할 수 있어 유연합니다.

**세 번째는 Batch Size 설정**입니다.
```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 1000
```
이렇게 하면 IN 쿼리로 한 번에 여러 개의 연관 엔티티를 조회합니다.

또한 **OSIV(Open Session In View)를 false로 설정**하여 N+1 문제를 명시적으로 해결하도록 강제했습니다. 이렇게 하면 지연 로딩 시 예외가 발생하므로, Fetch Join이나 EntityGraph를 사용해야 합니다.

Real MySQL 8.0 책을 통해 실행 계획을 분석하는 방법도 학습했고, 실제로 EXPLAIN으로 쿼리를 확인하면서 최적화했습니다."

#### Q3: React Query를 어떻게 활용했나요?

"React Query는 서버 상태 관리의 핵심 도구로 활용했습니다. 크게 세 가지 방식으로 사용했습니다.

**첫째, 데이터 페칭과 캐싱**입니다.
```typescript
const { data, isLoading } = useQuery({
  queryKey: ['correlation-source', perfTestId, pagination],
  queryFn: () => fetchCorrelationSource(perfTestId, pagination),
  staleTime: 1000 * 60 * 5,
  gcTime: 1000 * 60 * 10,
});
```
`queryKey`로 캐시를 식별하고, 동일한 키는 중복 요청을 하지 않습니다. `staleTime`은 데이터가 신선한 시간이고, `gcTime`은 사용하지 않는 캐시를 보관하는 시간입니다.

**둘째, 조건부 쿼리**입니다.
```typescript
const { data } = useQuery({
  queryKey: ['data', perfTestId],
  queryFn: () => fetchData(perfTestId),
  enabled: !!perfTestId,
});
```
`enabled` 옵션으로 perfTestId가 있을 때만 실행되도록 했습니다. 이렇게 하면 불필요한 API 요청을 방지할 수 있습니다.

**셋째, Mutation과 캐시 무효화**입니다.
```typescript
const mutation = useMutation({
  mutationFn: updateData,
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ['data'] });
  },
});
```
데이터 변경 후 자동으로 관련 쿼리를 무효화하여 최신 데이터를 가져옵니다.

이러한 전략으로 불필요한 API 요청을 80% 감소시켰고, 로딩 상태와 에러 핸들링도 일관성 있게 관리할 수 있었습니다."

#### Q4: MSA 환경에서 데이터 일관성을 어떻게 보장하나요?

"Rally-Point 프로젝트에서 MSA 아키텍처를 설계하면서 데이터 일관성 문제를 고민했습니다.

**첫째, 이벤트 기반 아키텍처**를 채택했습니다. Kafka를 사용하여 예약 생성/취소 시 이벤트를 발행하고, 관련 서비스들이 이를 구독하여 처리합니다. 예를 들어:
```json
{
  "type": "RESERVATION_CREATED",
  "reservationId": "abc123",
  "userId": "user456",
  "courtId": "courtA",
  "timestamp": "2024-06-25T15:00:00Z"
}
```

**둘째, Saga 패턴**을 적용하려고 합니다. 예약 생성 시 결제, 알림 등 여러 서비스가 연동되는데, 한 단계가 실패하면 보상 트랜잭션(Compensation)으로 롤백합니다.

**셋째, 분산 락**을 사용합니다. Redis의 Redisson을 활용하여 동시 예약 방지를 구현했습니다:
```
lock:reservation:{date}:{time}:{courtId}
```

**넷째, 메시지 보장**을 위해 Kafka의 at-least-once 전략과 idempotent 처리를 적용합니다. 실패한 메시지는 DLQ(Dead Letter Queue)로 보내 재처리합니다.

실무에서는 완벽한 강한 일관성보다는, **최종 일관성(Eventual Consistency)**을 목표로 하는 것이 현실적이라는 것을 학습했습니다."

#### Q5: 프로젝트에서 가장 어려웠던 기술적 문제는?

"Performance Tester 프로젝트에서 **불필요한 API 요청을 제거하는 것**이 생각보다 어려웠습니다.

초기에는 네트워크 탭을 보니 같은 API가 여러 번 호출되는 것을 발견했습니다. 원인을 분석해보니 세 가지 문제가 있었습니다.

**첫째, 중복 요청**이었습니다. 여러 컴포넌트에서 동일한 데이터를 요청하고 있었습니다. 이는 React Query로 해결했습니다. 동일한 `queryKey`를 사용하면 자동으로 캐시된 데이터를 사용하기 때문입니다.

**둘째, 조건 없는 요청**이었습니다. `perfTestId`가 없어도 API 요청을 시도해서 400 에러가 발생했습니다. `enabled: !!perfTestId` 옵션으로 해결했습니다.

**셋째, 무한 루프**였습니다. `useEffect`의 의존성 배열에 상태가 있어서, 상태 변경이 `useEffect`를 다시 트리거하는 문제였습니다. React Query로 전환하면서 이 문제도 해결됐습니다.

최종적으로 네트워크 요청을 80% 감소시켰습니다. 이 과정에서 **문제를 명확히 정의하고, 측정하고, 점진적으로 개선하는 것**의 중요성을 배웠습니다."

#### Q6: 팀원과 의견 충돌이 있었다면 어떻게 해결했나요?

"Performance Tester 프로젝트에서 백엔드 팀원과 API 스펙을 논의할 때 의견 차이가 있었습니다.

저는 프론트엔드에서 **페이징을 클라이언트 사이드에서 처리**하고 싶었고, 백엔드에서는 전체 데이터를 한 번에 주면 된다고 생각했습니다. 하지만 데이터가 10,000개 이상이 될 수 있다는 것을 알고, 서버 사이드 페이징이 필요하다는 것을 설득했습니다.

**해결 방법:**
1. **데이터로 설득**: 10,000개 데이터를 전송하면 약 5MB가 된다는 것을 계산해서 보여줬습니다.
2. **프로토타입 제시**: 1000개씩 페이징한 것과 전체를 받은 것의 성능 차이를 측정해서 보여줬습니다.
3. **타협점 찾기**: 페이지 크기를 1000개로 설정하여 API 요청 횟수도 줄이고, 성능도 확보했습니다.

결과적으로 백엔드에서도 페이징 API를 구현해줬고, 프론트엔드에서는 TanStack Query로 효율적으로 관리할 수 있었습니다. 이 과정에서 **데이터와 프로토타입으로 설득하는 것**의 중요성을 배웠습니다."

### 7.4 성장 관련 질문

#### Q7: 어떻게 기술을 학습하나요?

"저는 **이론 학습 → 실전 적용 → 문서화**의 사이클로 학습합니다.

**첫째, 책과 강의로 이론을 학습**합니다. Real MySQL 8.0, 자바의 신 등 6권 이상의 기술 서적을 읽었고, 각 챕터마다 핵심 개념을 Obsidian에 정리했습니다.

**둘째, 프로젝트에 즉시 적용**합니다. 예를 들어, TanStack Query를 학습한 직후 Performance Tester 프로젝트에서 전체적으로 활용했습니다. 실제 문제를 해결하면서 학습하는 것이 가장 효과적이었습니다.

**셋째, MOC(Map of Content)로 체계적으로 정리**합니다. Spring, Java, Database 등 주제별로 학습 내용을 연결하고, 프로젝트 경험과 링크를 만듭니다. 이렇게 하면 나중에 복습할 때 빠르게 찾을 수 있습니다.

**넷째, 일일 로그를 작성**합니다. KPT 형식(Keep, Problem, Try)으로 오늘 배운 것, 문제점, 시도할 것을 기록합니다.

이러한 학습 습관 덕분에 React 19나 TanStack 같은 최신 기술도 빠르게 습득할 수 있었습니다."

#### Q8: 앞으로 어떤 개발자가 되고 싶나요?

"저는 **기술적 깊이와 비즈니스 이해를 모두 갖춘 개발자**가 되고 싶습니다.

**단기적으로는(1년 내)**, 테스트 코드 작성 능력을 향상시키고, CI/CD 파이프라인을 구축하여 코드 품질을 높이고 싶습니다. 또한 Spring Cloud와 MSA 고도화를 통해 대규모 시스템을 설계할 수 있는 능력을 갖추고 싶습니다.

**중기적으로는(3년 내)**, 시스템 아키텍처를 설계할 수 있는 능력을 갖추고 싶습니다. 대규모 트래픽을 처리하고, 장애에 대응하며, 비용을 최적화하는 경험을 쌓고 싶습니다.

**장기적으로는**, 팀을 리드하고 기술 문화를 만드는 개발자가 되고 싶습니다. 코드 리뷰, 멘토링, 기술 블로그 작성을 통해 팀과 커뮤니티에 기여하고 싶습니다.

하지만 가장 중요한 것은 **사용자에게 가치 있는 서비스를 만드는 것**입니다. 기술은 수단이고, 궁극적으로는 사용자의 문제를 해결하는 개발자가 되고 싶습니다."
