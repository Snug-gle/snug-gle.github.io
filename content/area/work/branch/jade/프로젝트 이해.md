## 전체 개념 흐름
- JMeter 기반 성능/부하 테스트 자동화를 AI로 돕는 구조
- 사람이 손으로 하던 JMeter 스크립트 튜닝(코릴레이션, 규칙 생성)”을 AI가 제안해주도록 하는 것
## 각 파일 역할과 생성 과정

### 1. petstore_ff_doc.jmx
- **형식:** JMX (XML 기반)    
- **설명:**
    - JMeter에서 사용하는 **테스트 스크립트**.
    - HTTP Sampler, Header Manager, Assertion, ThinkTime 등 테스트 실행에 필요한 요소들이 들어있음.
    - 사람이 직접 만들 수도 있고, HAR → JMX 변환 도구나 JMeter Recorder를 통해 자동 생성할 수도 있음.
    - 여기서는 **최종 실행/튜닝 대상 스크립트**라고 보면 됨.
---
### 2. petstore_ff_doc_rec.jtl
- **형식:** JTL (CSV/XML, 실행 로그)
- **설명:**
    - JMeter Recorder 또는 실행 시 만들어지는 **요청/응답 기록 파일**.
    - 여기엔 HTTP 요청/응답 전문(request/response body, headers, querystring, status code 등)이 모두 들어 있음.
    - 즉, **“실제 사용자가 보낸 요청과 서버가 돌려준 응답”을 그대로 담고 있는 기록**.
    - 이 데이터를 분석해야 “어떤 값이 동적으로 변하는지” (= 세션ID, 토큰, 쿠키 같은 것들) 알 수 있음.
---
### 3. PY규칙컨피그001.csv
- **형식:** CSV (프로그램 생성)
- **설명:**
    - JMX 스크립트(`.jmx`)에서 **입력 데이터 요소를 추출**해서 만든 규칙 정의 파일.
    - 예를 들어, JMX 안의 Sampler 요청 body, querystring, header 등을 파싱 → 변수 후보(파라미터 이름, 값)를 정리.
    - 여기서 규칙은
        - "이 필드는 고정값으로 둔다"
        - "이 필드는 외부 CSV 데이터에서 가져온다"
        - "이 필드는 응답에서 추출해야 한다"  
            같은 정보를 담는 **매핑 설정(config)** 역할.
            
    - 결국 **JMeter Parameterization + Correlation의 초기 설정 파일**.
---
### 4. `PY코리후보001.csv`
- **형식:** CSV (프로그램 생성)
- **설명:**
    - `규칙컨피그` + `레코딩 JTL` 을 비교 분석해서 **코릴레이션(값 치환) 후보**를 도출한 결과물.
    - 예를 들어:
        - 로그인 요청 → 응답 JSON 안에 `sessionId=abc123`
        - 다음 요청 → `sessionId=abc123`을 그대로 전송함
        - → 이때 `abc123`은 매 실행마다 달라지므로, AI가 “이건 코릴레이션해야 한다”고 후보를 추천.
    - 즉, **응답에서 추출해야 할 동적 변수 후보 목록**을 정리한 파일.
    - 사람이 일일이 눈으로 요청/응답 비교하지 않고, 프로그램이 패턴을 찾아 CSV로 던져줌.
---
## 요약: 핵심 개념

1. **JMX (테스트 스크립트)**  
    → 실행할 테스트 시나리오 (HTTP 요청 정의)
    
2. **JTL (레코딩/실행 결과)**  
    → 실제 요청/응답 기록 (변수 추적용 데이터 원본)
    
3. **규칙컨피그 CSV**  
    → JMX에서 뽑은 요청 파라미터/헤더/쿼리 값 → 어떻게 처리할지 규칙 정의
    
4. **코릴레이션 후보 CSV**  
    → 규칙컨피그와 JTL을 대조 → “이 값은 동적으로 변하니 응답에서 추출 필요”라고 자동 추천
---
즉,

> **“HAR → JMX 변환 → 규칙 컨피그 생성 → JTL과 대조 → 코릴레이션 후보 추출”**  
> 이 프로젝트의 자동화 파이프라인이라고 보면 됩니다.
