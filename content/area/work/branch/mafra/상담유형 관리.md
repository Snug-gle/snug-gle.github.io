- 화면 단에서 상담유형별 스크립트를 어떻게 보여주면 좋을지? 
	- 기존 시나리오: 상담유형 스크립트 저장 버튼 클릭 시에 스크립트 eid가 없으면 저장, 스크립트 eid가 있으면 업데이트 
	- 현재 모습: 상담유형 스크립트 저정 버튼 클릭 시에 스크립트 eid 확인하지 않고 계속 저장
	- 고려사항
		- 저장 버튼 외에 수정, 삭제 버튼이 있어야 할지?
		- 위 버튼이 추가 된다면 사용자 경험 상 스크립트 리스트들을 확인할 수 있어야 하지 않을까?
- 단방향 VS 양방향
	- 단순히 추가 저장이 가능하게 한다면 "단방향"
	- 양방향 관계 시에는 지연 로딩 혹은 순환 참조 등 이슈가 발생할 수 있어 가급적 단방향으로 하고자 함
	- "리스트로 관리할 수 있다"라는 의미가 상담유형 엔티티를 통해 스크립트 리스트를 가져와야 하는 경우 (ex. 상담유형엔티티.getScript()  or getScriptList()) 에는 양방향 구조 고려

## 비교 포인트: 구분자 방식 vs. Converter(JSON) 방식

| 항목              | 구분자 방식 (String 필드)                     | Converter 방식 (List<String> 필드 + JSON 저장) |
| --------------- | -------------------------------------- | ---------------------------------------- |
| 필드 타입           | `String`                               | `List<String>`                           |
| DB 저장 형태        | `01012345678,0212345678` (콤마로 구분된 문자열) | `["01012345678","0212345678"]` (JSON 배열) |
| 변환 로직           | 서비스/컨트롤러에서 직접 `join()`, `split()`      | `@Converter`에서 자동 처리                     |
| 검색              | `LIKE '%0101234%'` (가능, but 부정확)       | `JSON_CONTAINS()` 등 JSON 함수 필요           |
| 삭제              | 문자열 파싱 후 삭제 → 다시 join                  | JSON 파싱 후 삭제 → 다시 저장                     |
| DB 제약           | 단일 컬럼 (TEXT, VARCHAR)                  | JSON 컬럼 필요 (MySQL 5.7+, Postgres 등)      |
| 성능              | 문자열 처리 성능                              | JSON 처리 성능 (약간 무거움)                      |
| 유지보수            | 구분자 위치 실수 위험                           | JSON 파싱/생성 코드 필요, 더 깔끔함                  |
| 확장성 (다른 데이터 추가) | 별도 파싱 로직 필요                            | JSON 구조 확장 쉬움 (`[{phone, type}]` 등)      |
