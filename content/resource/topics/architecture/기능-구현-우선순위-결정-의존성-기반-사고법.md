# 🎯 기능 구현 우선순위 결정 - 의존성 기반 사고법

## 📌 핵심 원칙

> **"의존성 방향을 따라간다"**
>
> 소비자(Consumer)는 제공자(Provider)에 의존한다.
> 제공자를 먼저 정의해야 소비자가 구현 가능하다.

### 기본 흐름
```
DB 스키마 → 백엔드 API → 프론트엔드 UI
```

- **DB**: 데이터의 근원, 모든 것의 시작점
- **백엔드**: DB를 소비하고, 프론트엔드에 제공
- **프론트엔드**: 백엔드 API를 소비하고, 사용자에게 제공

---

## 🔍 실제 구현 순서

### 1단계: 계약(Contract) 정의 📋

먼저 양측이 합의할 **인터페이스**를 정의한다.

```typescript
// 백엔드와 프론트엔드가 합의하는 계약
interface CursorPageResponse<T> {
  items: T[];
  nextCursor: string | null;
  hasNext: boolean;
  size: number;
}

interface LinkDto {
  id: string;
  url: string;
  title: string;
  tags: string[];
}
```

> [!tip] 계약 우선의 장점
> - 백엔드/프론트엔드가 병렬 작업 가능
> - 인터페이스가 변경되면 양측 모두 컴파일 에러로 즉시 감지
> - Mock 데이터로 독립적 개발 가능

### 2단계: 백엔드 구현 (하향식)

```
DB 테이블 → Repository → Service → Controller
```

#### 2-1. DB 스키마
```sql
CREATE TABLE links (
  id VARCHAR(36) PRIMARY KEY,
  user_id VARCHAR(36) NOT NULL,
  url VARCHAR(2048) NOT NULL,
  title VARCHAR(255),
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_user_created (user_id, created_at)
);
```

#### 2-2. Repository (데이터 접근 계층)
```java
@Mapper
public interface LinkMapper {
    List<Link> findByCursor(
        @Param("userId") String userId,
        @Param("cursor") String cursor,
        @Param("size") int size
    );
}
```

```xml
<!-- MyBatis 쿼리 -->
<select id="findByCursor" resultType="Link">
    SELECT * FROM links
    WHERE user_id = #{userId}
    <if test="cursor != null">
        AND created_at &lt; #{cursor}
    </if>
    ORDER BY created_at DESC
    LIMIT #{size} + 1
</select>
```

#### 2-3. Service (비즈니스 로직)
```java
@Service
@RequiredArgsConstructor
public class LinkService {
    private final LinkMapper linkMapper;
    private final CursorUtils cursorUtils;

    public CursorPageResponse<LinkDto> getLinks(String userId, String cursor, int size) {
        List<Link> results = linkMapper.findByCursor(userId, cursor, size);

        boolean hasNext = results.size() > size;
        List<Link> items = hasNext ? results.subList(0, size) : results;

        String nextCursor = hasNext
            ? cursorUtils.encode(results.get(size).getCreatedAt())
            : null;

        return CursorPageResponse.<LinkDto>builder()
            .items(items.stream().map(LinkDto::from).toList())
            .nextCursor(nextCursor)
            .hasNext(hasNext)
            .size(items.size())
            .build();
    }
}
```

#### 2-4. Controller (API 엔드포인트)
```java
@RestController
@RequestMapping("/api/links")
@RequiredArgsConstructor
public class LinkController {
    private final LinkService linkService;

    @GetMapping
    public ResponseEntity<CursorPageResponse<LinkDto>> getLinks(
        @RequestParam(required = false) String cursor,
        @RequestParam(defaultValue = "20") int size
    ) {
        String userId = SecurityContextHolder.getContext()
            .getAuthentication().getName();
        return ResponseEntity.ok(linkService.getLinks(userId, cursor, size));
    }
}
```

### 3단계: 프론트엔드 구현 (하향식)

```
타입 정의 → API 레이어 → 훅 → UI 컴포넌트
```

#### 3-1. 타입 정의 (백엔드 계약 복제)
```typescript
// types/link.ts
export interface CursorPageResponse<T> {
  items: T[];
  nextCursor: string | null;
  hasNext: boolean;
  size: number;
}

export interface LinkDto {
  id: string;
  url: string;
  title: string;
  tags: string[];
}
```

#### 3-2. API 레이어
```typescript
// api/linkApi.ts
import axios from 'axios';
import { CursorPageResponse, LinkDto } from '@/types/link';

export const linkApi = {
  getLinks: async (cursor?: string, size = 20): Promise<CursorPageResponse<LinkDto>> => {
    const response = await axios.get('/api/links', {
      params: { cursor, size }
    });
    return response.data;
  }
};
```

#### 3-3. React Query 훅
```typescript
// hooks/useInfiniteLinks.ts
import { useInfiniteQuery } from '@tanstack/react-query';
import { linkApi } from '@/api/linkApi';

export const useInfiniteLinks = (size = 20) => {
  return useInfiniteQuery({
    queryKey: ['links'],
    queryFn: ({ pageParam }) => linkApi.getLinks(pageParam, size),
    getNextPageParam: (lastPage) =>
      lastPage.hasNext ? lastPage.nextCursor : undefined,
    initialPageParam: undefined
  });
};
```

#### 3-4. UI 컴포넌트
```typescript
// components/LinkList.tsx
import { useInfiniteLinks } from '@/hooks/useInfiniteLinks';

export const LinkList = () => {
  const { data, fetchNextPage, hasNextPage, isFetchingNextPage } = useInfiniteLinks();

  return (
    <div>
      {data?.pages.map((page) =>
        page.items.map((link) => (
          <LinkCard key={link.id} link={link} />
        ))
      )}

      {hasNextPage && (
        <button onClick={() => fetchNextPage()} disabled={isFetchingNextPage}>
          {isFetchingNextPage ? '로딩 중...' : '더 보기'}
        </button>
      )}
    </div>
  );
};
```

## 🛠 순서 결정 방법: 역방향 추적

### "이걸 구현하려면 무엇이 필요한가?" 질문하기

| 구현하려는 것 | 질문 | 필요한 선행 조건 |
| :---------- | :--- | :------------- |
| 🖼 UI 컴포넌트 표시 | 데이터는 어디서? | 훅이 데이터를 줘야 함 |
| 🔄 훅 호출 | 훅은 뭘 호출? | API가 있어야 호출 |
| 📡 API 호출 | 어디로 요청? | 백엔드 엔드포인트 필요 |
| 🎮 Controller | 누가 로직 처리? | Service가 로직 처리 |
| 🧠 Service | 데이터는 어디서? | Repository가 데이터 조회 |
| 📦 Repository | 뭘 조회? | DB 테이블 존재 |
| 🗄 DB 테이블 | - | 시작점 |

### 구현 순서 (의존성 해소)
```
1. DB 테이블 생성
2. Repository 구현
3. Service 구현
4. Controller 구현
5. 타입 정의
6. API 레이어 구현
7. 훅 구현
8. UI 컴포넌트 구현
```

## 🚀 병렬화 전략

### Mock을 활용한 병렬 작업

계약(인터페이스)이 정해지면, Mock 데이터로 백엔드와 프론트엔드를 병렬로 개발할 수 있다.

#### 백엔드 팀
```java
// 실제 API 구현
@Service
public class LinkService {
    // 실제 DB 조회 로직
}
```

#### 프론트엔드 팀
```typescript
// Mock 데이터로 UI 개발
const mockLinkApi = {
  getLinks: async (): Promise<CursorPageResponse<LinkDto>> => {
    return {
      items: [
        { id: '1', url: 'https://example.com', title: 'Example', tags: [] }
      ],
      nextCursor: 'abc123',
      hasNext: true,
      size: 1
    };
  }
};
```

#### 통합 시점
```typescript
// 개발 환경에 따라 Mock/실제 API 전환
const linkApi = process.env.USE_MOCK
  ? mockLinkApi
  : realLinkApi;
```

> [!tip] 병렬 작업의 이점
> - 개발 속도 향상 (블로킹 없음)
> - 프론트엔드가 백엔드 완성을 기다리지 않음
> - 계약 검증이 빨라짐 (타입 불일치 조기 발견)

## 💡 판단 기준 4가지

### 1. 의존성 분석
**질문**: A가 B 없이 동작할 수 있는가?

```typescript
// ❌ UI는 훅 없이 동작 불가
function LinkList() {
  const { data } = useInfiniteLinks(); // 훅 의존
  // ...
}

// ✅ 훅은 UI 없이도 테스트 가능
const { result } = renderHook(() => useInfiniteLinks());
```

**원칙**: 의존되는 것을 먼저 구현한다.

### 2. 계약 우선 (Contract-First)
**질문**: 인터페이스가 정의되었는가?

```typescript
// 1순위: 계약 정의
interface LinkDto {
  id: string;
  url: string;
  title: string;
}

// 2순위: 구현 (백엔드/프론트엔드 병렬)
```

**원칙**: 타입과 인터페이스를 먼저 설계한다.

### 3. 테스트 가능성
**질문**: 이 코드를 독립적으로 검증할 수 있는가?

```java
// ✅ Service는 독립적으로 테스트 가능
@Test
void getLinks_shouldReturnCursorPage() {
    // given
    when(linkMapper.findByCursor(any(), any(), anyInt()))
        .thenReturn(mockLinks);

    // when
    CursorPageResponse<LinkDto> result = linkService.getLinks("user1", null, 20);

    // then
    assertThat(result.getItems()).hasSize(20);
}
```

**원칙**: 하위 계층부터 구현하면 단위 테스트가 쉽다.

### 4. 병렬화 가능성
**질문**: Mock으로 대체 가능한 의존성인가?

```typescript
// Mock 가능 → 병렬 작업 가능
const mockApi = {
  getLinks: jest.fn().mockResolvedValue(mockData)
};

// Mock 불가능 → 순차 작업 필요
// (예: DB 스키마는 Mock 불가, 실제로 존재해야 함)
```

**원칙**: Mock 가능하면 병렬, 불가능하면 순차.

## ✅ 실전 적용 체크리스트

### 새 기능 구현 시
- [ ] 1. 요구사항 분석: 무엇을 만들 것인가?
- [ ] 2. 계약 정의: 백엔드-프론트엔드 인터페이스 합의
- [ ] 3. 의존성 추적: 역방향으로 "이걸 하려면 뭐가 필요?"
- [ ] 4. 순서 결정: 의존되는 것부터 구현
- [ ] 5. 병렬화 검토: Mock으로 대체 가능한가?
- [ ] 6. 구현: 하위 계층 → 상위 계층
- [ ] 7. 통합 테스트: 전체 플로우 검증

### 우선순위 판단이 어려울 때
```
"이걸 구현하려면 무엇이 필요한가?"
→ 필요한 것이 먼저 구현되어야 한다.

"A가 B에 의존하는가, B가 A에 의존하는가?"
→ 의존받는 것(Provider)을 먼저 구현한다.

"Mock으로 대체할 수 있는가?"
→ 가능하면 병렬, 불가능하면 순차.
```
